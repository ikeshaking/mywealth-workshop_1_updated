01 · End-to-end flow

The pipeline: advice request → Word document

Seven stages. The advice request chooses what to say; the word bank and template rules supply the words; the uploaded documents supply the figures; a final pass resolves tokens and drops the wording that doesn't apply to this client.

1

Advice Request Builder → advice-request JSON

The adviser ticks strategies per area and sets the framing. Output is a JSON the generator ingests: soaType, ctype, scopeIn/scopeOut, strategies[] (each with area, name, est, owner), superProducts / insProducts / invProducts, risk, paraplanning.

2

Ingest & route to blocks

Each strategy's area maps to a document block via V200_AREA_TO_BLOCK, and area :: name is the key into the word bank.

3

Word bank lookup → block content

For every strategy, V200_WORD_BANK["area::name"] yields its strat / why / risks / alts / comments / altProducts / adminFees. Tokens ([Name], <super fund>, per-person expansion) resolve, and the text is written to B[block].content.{recommendation,why,risks,alternatives,…}.

4

Standard-template post-passes (the “when X / when Y” rules)

A fixed chain of conditional passes runs in order — each fires on a flag derived from the advice request or an uploaded doc, and adds / swaps / strips wording. Runs roughly: SOA type → products & approach → super → debt → cashflow → insurance → risk → fees → scope-out.

02 · Does all tailored wording link to the word bank?

Mostly — but not all. Three sources feed the document.

The honest answer to “is every tailored line triggered from the advice-request word bank?” is: the strategy narrative is, comprehensively. But two other sources also write wording — data-driven builders (for anything that must reconcile to a parsed figure) and a fixed static layer (legal appendices). Knowing which is which is the whole audit trail.

Word-bank driven (advice-request-gated) Built in code (data / figure-driven) Static template layer
Word-bank driven

Triggered by area::name in the advice request

The Recommendation / Why / Risks / Alternatives for every scoped strategy, across all 10 mapped areas. One tick in the builder → one word-bank scenario → one set of bullets.

  • Debt — offset, surplus, tax, gearing, term-loan, consolidation…
  • Super — full/partial rollover, retain, consolidate, DB, military, SMSF, pension/TTR…
  • Contributions — salary sacrifice, carry-forward, NCC, spouse, downsizer…
  • Insurance — new / top-up / replace-takeover / retain, per cover & definition…
  • Investment plan · property · bond · cashflow · estate · admin
Built in code

Data-driven — must reconcile to a parsed figure or table

These are not free-text word-bank entries because they are computed from an uploaded document or a table, and the words change with the numbers.

  • Insurance “Why” — buildInsuranceWhyText() from the quote/covers
  • Cashflow MCMA — CF_* constants + figure injection
  • Per-fund super replacement table — v210SuperReplPerFund()
  • CARE fees / franking — v49 franking, careFees, from the CARE doc
  • Super/invest alternatives — v200BuildSuperAltFromWS(), v200ApplyCareInvestBlocks() from WealthSolver / CARE allocation

The static layer (source #3). The general-advice warning and the “Understanding Risk” appendix are the same in every SOA — a fixed annexure, not adviser-authored. In the exemplar audit these read as “missing” from the word bank only because they were never meant to live there. Recommended: add them once as a static annexure block (the single largest coverage win).

Advice Request Builder — fields it already carries

The builder already emits the shape the generator consumes: soaType, ctype, per-area strategies[] with est product/amounts/source, superProducts (incl. disposition), insProducts.action, invProducts, scopeIn/Out, risk, paraplanning. The remaining alignment work is additive — surface the new scenarios above as tick options, and expose the CARE-vs-Vanguard per-section approach as an explicit toggle (today it is inferred from the uploaded CARE doc).

The one-sentence readiness statement. The strategy narrative is comprehensively advice-request-driven and figure-accurate on wired paths; each genuinely new client shape still surfaces a one-time wiring add (the exemplar harness now finds these systematically rather than one SOA at a time). Treat it as a high-quality first-draft engine with adviser sign-off — not an autopilot — until the coverage map is green.

1. Executive summary

The SOA generation toolchain converts an adviser's structured Advice Request, plus the client's supporting documents, into a draft Statement of Advice in the firm's house style. It exists to make SOA production faster, more consistent and more complete — every recommendation the firm makes routinely arrives with its approved recommendation wording, "why this benefits you" reasoning, risks, and alternatives considered, drawn from a single reviewed word bank rather than re-typed (and re-varied) for each file.

Three design principles run through the whole system:

  • One source of truth for wording. All tailored wording lives in the Words Masterlist (163 modules). The Advice Request Builder's 118 strategy ticks map 1:1 onto it — verified programmatically, currently zero unmapped ticks — so nothing an adviser can request will silently arrive without approved wording.
  • Fail loudly, never silently. Anything the system cannot confidently resolve is either surfaced in a post-import "still needs your attention" report, or left in the document as an unmissable placeholder ($XXX, yellow-highlighted bracket choices). The system never guesses between two plausible matches.
  • Human in the loop. The output is a draft. The adviser/paraplanner confirms every file mapping before import, resolves every flagged gap, and reviews the document before it goes near a client. The tool standardises wording and assembly; it does not determine whether advice is appropriate.

3. System components

3.1 Advice Request Builder (MWS_Advice_Request_Builder_4.html)

A single-file web form the adviser completes after the strategy meeting. It captures: SOA type (accumulation / retirement), client(s) and adviser, new / existing status, entities (SMSF / company / trust), the "Hi team" narrative, risk profile per client (and per entity), scope in / scope out per advice area, the strategy ticks (118 across 8 advice areas, each with the firm's default recommendation line and any dollar/percentage slots), product selections (super platform, recommended insurer per client), and the fee matrix. It exports the Advice Request as JSON (machine-readable, the generator's source of truth) and as a Word document (the human-readable paraplanning request).

3.2 Words Masterlist (SOA_Words_MasterList.json / .docx)

The firm's tailored-wording register: 163 modules, of which 148 are linked to builder ticks and 15 are standing rules (openers, scope wording, CARE philosophy justifications). Each module holds the trigger (tick name), keyword trigger phrases, mode and scope gate, and the SOA wording: recommendation line, why, risks, alternatives, outcome. The Word version is generated from the JSON, so the two cannot drift. Section 5 covers how it is matched and edited.

3.3 SOA Generator (SOA_Generator_v190_38.html (rev. v190_38l))

A single-file web application (runs locally in a browser; no server, no data leaves the machine). It holds the SOA as 36 sections ("blocks"), each with standard wording plus the tailored content written in by imports. Its smart drop accepts any batch of files, classifies each, routes it to the right client, and applies everything in a fixed, safe order. A live preview mirrors the Word output; export produces the .docx via the embedded docx library.

4. End-to-end data flow

1
Adviser completes the Advice Request Builder
Ticks strategies, sets scope, risk profiles, products, fees and entities. Downloads the Advice Request JSON (+ Word copy for the file).
2
Paraplanner gathers the supporting documents
Wealth Projector fact-find JSON, data collection sheets (Excel/PDF), CARE portfolio doc, WealthSolver comparison, Risk Researcher, insurer quotes, existing-cover quote, commission reports.
3
Everything is dropped onto the generator in one batch
Each file is read and classified; client/partner routing is proposed from document content and filename. The paraplanner confirms the mapping in the smart-drop modal before anything is applied.
4
Deterministic apply pipeline
Regardless of drop order, files apply as: word bank → fact-find JSON → Advice Request → data collection → CARE → WealthSolver → Risk Researcher → insurer quotes → existing-cover quote → commissions. Identity loads before per-person documents; premiums exist before commission maths.
5
Advice Request drives the word bank
Each strategy tick is looked up in the word bank (exact key → normalised → unique containment; never a guess between two candidates). Matched modules write the recommendation / why / risks / alternatives into the right SOA section; scope flags activate sections; framing items set new/existing-client wording; entities activate the entity section. Every miss is recorded and reported.
6
Gap & conflict reporting, then human editing
The import summary lists what applied, what was skipped, importer warnings, unmatched strategies and empty key figures. A conflicts panel flags scope-vs-projector mismatches. The paraplanner edits any section directly; unresolved figures remain as $XXX / yellow placeholders that cannot be missed.
7
Render safety nets, then Word export
On every render and again at export: scaffolding stripped, template conditionals resolved for the scenario, per-person tables built for couples, duplicate rows/lines de-duplicated, product defaults applied, cost lines computed from the replacement tables, token backfills. The exported .docx matches the live preview.

5. The word-bank concept

Every module is keyed "Area::Strategy name" (e.g. "4 · Investment Plan::Add a reserves portfolio") and carries five wording fields:

FieldLands in the SOA as
stratThe recommendation bullet(s) in the strategy table — dollar slots filled from the builder's amounts, per-person expansion for couples where the strategy is per-person
why"Why this benefits you" list — de-duplicated across modules landing in the same section
risksThe section's risk list — de-duplicated
alts"Alternatives considered" — including why each was discounted
outcomeSummary — Outcomes line where applicable

Matching is tolerant but never speculative. A tick is matched to a module by exact key first; failing that, by a normalised form that ignores case, separators, punctuation and area numbering; failing that, by containment — but only if exactly one candidate contains (or is contained by) the tick name. Two plausible candidates = no match = a recorded miss, reported to the paraplanner. A missed tick still lands in the SOA as its builder default text, so nothing the adviser requested disappears — it just arrives without the why/risks/alternatives, and flagged.

Coverage is complete and provable. A three-way reconciliation (builder ticks ↔ word bank ↔ masterlist) is part of the release checks: all 118 builder ticks currently resolve, and the bank and masterlist are identical at 163 modules in both directions.

The wording is editable without touching the tools. Dropping an edited SOA_Words_MasterList.json onto the generator replaces its live word bank (adds, rewordings and removals take effect, with counts reported). Dropping a small fragment keyed "Area::Name" merges — for adding or rewording individual modules. The masterlist Word document is generated from the JSON, so the readable register always matches what the tools actually use.

This is the compliance heart of the system: the wording clients receive is not whatever a paraplanner typed that day — it is the reviewed register, applied mechanically, with every exception flagged.

8. Verification & testing

  • Automated regression: 12 headless-browser test suites (~180 individual checks) covering import classification and routing, couple rendering across all four table families, CARE single- and two-document workflows, insurer comparison maths, drag-and-drop order independence, the ATP compliance block, word-bank matching and editability, entity consumption, and the render safety nets. All suites pass on the shipped build; they run against the actual HTML file, not a mock.
  • Exemplar parity: output structure and wording verified against six real SOAs spanning the scenario matrix — two accumulation couples, a couple + SMSF entity, a dual-adviser couple, a single existing client, and a dual-adviser single. In addition, the Borgh SOA (couple, Zurich Active + NEOS, Military Super, existing-cover increase) reproduces its presented exemplar on all 52 conformance checks, and the Robinson SOA insurance section scores 13/13 against its exemplar on the exported Word document.
  • Reviewer-comment cycle: over 90 annotated comments across multiple reviewed drafts (Robinson, Borgh, Fisher) were individually triaged, fixed and re-verified with targeted automated checks — including the Borgh draft (19 comments) and the Robinson rob2 draft (10 comments).
  • Coverage reconciliation: builder ticks ↔ word bank ↔ masterlist checked programmatically in both directions; currently 118/118 ticks resolve and 163 = 163 modules.

9. Known limitations & human checkpoints

  • The tool assembles and standardises; it does not assess suitability. The Advice Request remains the adviser's professional determination.
  • Figures are only as good as the source documents. A wrong balance in the fact-find flows through — the gap report catches missing figures, not incorrect ones.
  • Free-text strategies (custom recommendations outside the 118 ticks) arrive without why/risks/alternatives and are flagged for manual completion. If a custom strategy becomes routine, add it to the masterlist (Section 10).
  • Scanned/image-only PDFs cannot be read; the paraplanner keys those figures manually and the gap report will show what's missing.
  • The Word export is now machine-verified headlessly — a docx-export check compares the exported document against the on-screen preview on every regression run, so preview/export divergence is caught automatically rather than by visual spot-check. OCR of scanned or image-only PDFs remains out of scope.
  • Multi-entity structures beyond one advice entity render the first entity's details in the entity fields; additional entities' wording lands in the Entity Strategies section but complex multi-entity covers remain a manual layout task.
  • Annexures are deliberately out of scope and produced separately.
Mandatory checkpoints before an SOA leaves paraplanning: (1) the smart-drop completion report shows no unresolved skips or warnings; (2) the attention list is empty; (3) no $XXX or yellow-bracket placeholder remains; (4) the conflicts panel is clear; (5) full read-through of the draft. These are procedural — the tool surfaces them but people close them.

10. Change management

  • Wording changes are made in SOA_Words_MasterList.json (directly, or by updating the Word register and mirroring to JSON), reviewed like any advice-wording change, then dropped onto the generator — which reports exactly how many modules were added, updated and removed. No code changes, no redeployment.
  • New builder ticks require a matching masterlist module (same area and name). The three-way reconciliation check (builder ↔ bank ↔ masterlist) is the release gate: zero unmatched ticks before a builder version ships.
  • Tool versions are single files with version-stamped names; superseded versions are retained. The automated suites are the regression gate for any generator change.
